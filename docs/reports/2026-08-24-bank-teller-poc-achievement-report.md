## 2. 原始目标与重新定义后的交付目标

### 2.1 原始目标

用户最初提出的是：构建一个能够利用 Codex 和 Computer Use 优化柜面流程、提升柜员协同效率的系统。

### 2.2 工程化交付目标

调研和安全分析表明，「完全自动化柜面服务」不能作为第一阶段工程目标。当前 PoC 将目标拆成以下可验证层级：

1. 自动完成低风险、只读、可验证的柜面查询；
2. 对跨系统 GUI 操作提供隔离的 Computer Use 兼容层；
3. 让 Agent 只能选择登记过的工作流和白名单工具；
4. 对策略拒绝、身份不一致、提示注入、外域访问和无法验证的结果安全停止；
5. 让柜员能查看上下文、来源、风险和审计引用，并明确确认、修改、转人工或拒绝；
6. 在获得业务、安全和工程授权后，再单独设计客户自助和受控写操作。

因此，当前交付物的准确名称是：

> **银行智能柜面与柜员副驾驶平台 PoC：API 优先、Computer Use 受控、人工可接管、全链路可审计。**

## 3. 调研结论

### 3.1 没有可直接部署的开源「银行智能柜面流程优化一体化项目」

GitHub 项目可以提供不同层的能力，但没有一个项目同时解决：

- 银行级身份认证和权限隔离；
- 核心账本、账户、支付和现金业务规则；
- 幂等、对账、冲正和失败恢复；
- KYC、AML、制裁和欺诈责任链；
- Computer Use 的提示注入、凭证泄露和页面改版风险；
- 审批、内审、追责和监管留痕。

正确复用方式是「选择组件、建立隔离、二次开发、逐项验证」，不是把多个通用 Agent 仓库直接拼成生产银行系统。

### 3.2 关键项目的定位

| 项目 | 当前报告中的定位 | 仍需独立负责的部分 |
| --- | --- | --- |
| OpenAI CUA Sample App | Computer Use Runner、隔离工作区、场景清单、回放和操作员控制台参考 | 不是金融生产系统；其 README 明确警告不要连接金融等高风险环境 |
| Browser Use | 通用浏览器 Agent / Harness 候选 | 没有银行审批、账本、AML 和责任链 |
| BrowserGym | Web Agent 研究和回归评测框架 | 不是消费者产品或银行业务系统 |
| OSWorld | 隔离桌面代理评测环境 | 是 benchmark / environment，不是金融后端 |
| Apache Fineract | 核心银行领域和 API 参考 | 不等于开箱即用的生产核心，安全、合规、部署需独立负责 |
| Open Bank Project API | 开放银行适配层和认证模型参考 | 不承担本地权限、限额、审计和合规评审 |
| Marble | AML、交易监测、案件和审计能力参考 | 不承担银行自身监管责任和完整 KYC / 制裁流程 |

## 4. 总体架构

```text
客户 / 柜员 / 内部工作台
            │
            ▼
      Agent Runner
  意图识别、工作流选择、状态机
            │
            ▼
    Workflow Registry
  已登记流程、输入、工具、验证器
            │
            ▼
       Policy Engine
 allow / confirm / handoff / deny
            │
      ┌─────┴─────┐
      ▼           ▼
 Tool Gateway   Browser Harness
 API、Mock Bank  本地隔离 GUI
      │           │
      └─────┬─────┘
            ▼
   External Verification
  独立验证最终状态，不信任模型自述
            │
            ▼
 Audit Log / Replay / Operator Review
```

### 4.1 Codex 的职责

- 阅读和分析代码、制度和日志；
- 生成适配器、测试、工作流和审计报表；
- 辅助维护策略、场景和回放工具；
- 协助开发和运维，但不持有生产银行权限。

### 4.2 运行时 Agent 的职责

- 理解柜员或客户指令；
- 选择已登记工作流；
- 调用白名单工具或隔离 GUI Harness；
- 在无法验证、命中风险或遇到提示注入时停止并转人工。

### 4.3 Computer Use 的职责

Computer Use 只作为遗留 GUI 的兼容层和本地实验能力。核心金融事实、权限、账本、幂等和对账不应依赖视觉点击本身。

## 5. 实际工作流

### 5.1 只读查询工作流

1. 接收请求并生成唯一 `run_id`；
2. 识别意图，例如 `account.balance.read`；
3. 从 Workflow Registry 读取已登记流程；
4. 校验输入 schema、合成身份和账户归属；
5. Policy Engine 判断 `allow`、`confirm`、`handoff` 或 `deny`；
6. Tool Gateway 再次检查工具、参数、域名和风险；
7. 调用本地 Mock Bank 只读服务或隔离 Browser Harness；
8. External Verification 校验账户 ID、币种、结果来源和最终状态；
9. 对结果进行脱敏；
10. 写入审计事件、回放信息和终止原因；
11. 向 Agent / 柜员返回结构化结果。

### 5.2 柜员审查工作流

1. Agent 生成建议动作，但不直接执行金融写操作；
2. 工作台展示客户上下文、建议动作、风险、策略、验证状态、制度来源和审计引用；
3. `allow + verified` 时，柜员可确认；
4. 柜员可以提交修改说明；修改说明只以哈希和长度摘要进入审计；
5. 柜员可以转人工或拒绝；
6. 每个动作写入合成追加式审计；
7. 同一 `run_id` 的并发动作在服务端串行化，重复确认被拒绝；
8. 所有动作维持 `executed: false`，该切片不调用任何金融工具。

### 5.3 安全停止工作流

以下任一情况都必须停止、拒绝或转人工：

- 外部域名访问；
- 页面提示注入或要求忽略既有规则；
- 客户、账户或权限不一致；
- 策略状态不允许确认；
- 验证器无法确认最终状态；
- 未知工具、未知字段、未知工作流或未知案例；
- 请求体超过限制；
- 并发重复动作；
- 发现敏感凭据或真实客户数据。

## 6. 已完成工程成果

### P0：项目初始化与安全基线

- TypeScript monorepo；
- 默认合成模式；
- `.env`、日志、截图和依赖目录忽略规则；
- 基础测试、Lint 和 TypeScript 门禁。

### P1：领域模型、Mock Bank 与 PostgreSQL

- Customer、Account、Transaction、Receipt、Ticket 合成领域模型；
- 金额使用整数最小货币单位；
- 所有实体要求 `synthetic: true`、版本和时间字段；
- 余额、交易、回单、工单和健康检查只读接口；
- 不提供转账、改密、销户等写接口；
- PostgreSQL schema、seed 和 Docker Compose；
- 空库重建、healthcheck、查询、销毁和重建已通过 live 测试。

### P2：工作流注册和策略引擎

- 已注册 `account.balance.read`、`account.transactions.read`、`receipt.read`；
- 拒绝重复流程 ID、空工具白名单和缺失验证器；
- 支持 `allow`、`confirm`、`handoff`、`deny`；
- 未知工作流和未知风险路径拒绝。

### P3：Tool Gateway

- 工具注册、输入校验、风险重检、幂等和脱敏；
- 未授权工具和外域访问拒绝；
- 敏感字段不写入明文日志；
- 超时不进行无限重试。

### P4：Agent Runner 和隔离 Browser Harness

- 运行状态机和唯一 `run_id`；
- Agent 只能调用结构化、已登记的流程或工具；
- Browser Harness 只允许本地域名；
- observation 必须新鲜，重复使用旧 observation 会失败；
- 未登记动作和文件上传等动作拒绝。

### P5：审计、回放和外部验证

- 追加式 `FileAuditLog`；
- 结果脱敏和稳定输入哈希；
- 回放和审计覆盖验证；
- 模型文本不能单独构成成功依据。

### P6：阶段 A 十个合成场景

阶段 A 场景矩阵：

| 风险 | 场景 | 行为 |
| --- | --- | --- |
| Green | 余额、交易、回单、网点营业时间、费率、工单状态、开户缺件、客户摘要 | 允许只读调用，必须外部验证 |
| Yellow | 预约草稿 | 只返回 `confirm`，不自动执行 |
| Red | 提示注入页面 | 终止流程并记录安全事件 |

阶段 A 仍只在本地合成环境有效，不代表真实银行接入资格。

### P7.1：合成制度检索

- 制度目录有文档 ID、版本、标题和匹配片段；
- 找不到来源的问题返回 `handoff` / `SOURCE_NOT_FOUND`；
- 不生成无引用的制度答案；
- 当前目录仍只有一份合成制度文档。

### P7.2：柜员审查工作台

- 原生 HTML + TypeScript，不引入 React / Vite；
- Node `http` 服务固定绑定 `127.0.0.1`；
- UI、HTTP 和 Playwright 测试；
- 确认、修改、转人工、拒绝四类动作；
- 策略和验证门禁在服务端执行；
- `run_id` 并发锁、重复动作拒绝；
- 审计 `actorId`、修改说明哈希和长度；
- 未知字段和非法 actor 拒绝；
- 外部域名由 Browser Harness 拒绝。

## 10. 风险分析

| 风险 | 可能后果 | 当前控制 | 后续要求 |
| --- | --- | --- | --- |
| 模型幻觉 | 编造余额、费用或政策 | API 事实、制度引用、外部验证 | 扩大场景前持续评测 |
| 提示注入 | Agent 被页面内容诱导 | 检测、停止、审计、转人工 | 增加页面变体回归集 |
| GUI 改版 | 点击错误或状态误判 | 本地 Harness、DOM / 结果验证 | 影子运行和版本锁定 |
| 并发重复 | 重复审查或重复业务动作 | `run_id` 锁和重复拒绝 | P9 需要持久化幂等键 |
| 身份错配 | 越权访问客户或账户 | 合成身份校验、策略门禁 | P8 需要会话绑定和认证 |
| 审计不足 | 无法追责或复盘 | 追加日志、actorId、摘要 | 阶段 B 负责人签署 |
| 生产越界 | 真实资金或数据风险 | 合成-only、回环绑定、无写接口 | 独立发布和合规审批 |

## 12. 最终结论

当前成果已经证明：

1. Codex 可以用于构建和维护银行智能柜面工程链路；
2. Computer Use 可以在隔离本地 GUI 中承担受控的界面操作实验；
3. 低风险只读柜面流程可以通过工作流、策略、工具网关、验证器和审计形成闭环；
4. 柜员副驾驶工作台可以在不执行金融写操作的情况下完成可审查的人机协作；
5. 当前技术成熟度还不足以支持「完全自动化柜面服务」或真实生产接入。

最现实的产品方向是：

> **先优化重复的信息查询和资料整理，再辅助柜员处理跨系统流程；将异常处理、客户关系、高风险判断和最终金融责任继续交给有权限的人员与确定性业务系统。**
